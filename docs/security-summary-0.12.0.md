# SpaceWorks 0.12.0 security verification

Security verification is tied to an exact source and image. This summary carries forward the [0.11.0 candidate summary](security-summary-0.11.0.md), whose results stay bounded to the inputs they were run on, and adds the 0.12.0 connections. Pending entries below do not establish a passing result. No final 0.12.0 image, full backend regression or browser suite has been verified yet.

| Area | Implemented protection | Verification status |
| --- | --- | --- |
| Authentication and API authority | Carried from 0.11.0. Revoking a person's authentication also ends their personal access tokens and deletes their OAuth tokens and app consents. The web telemetry settings endpoint requires a signed-in active account with no pending password change. Linked mutations (loan context, repair handoff, Shop pickup move) refuse bearer clients; the event booking link is session-only for reads and writes. | Pending: real PAT/OAuth/HMAC and session cases, including ordinary stock use still allowed and linked mutations denied to bearer clients, and revocation of every credential type. |
| Tenant isolation and authority | New linked views (related facts, event linked finance, loan-context reports, kits and proposals) read each section from its own owner, gated by that source's module and authority, and omit hidden sections. Context changes recheck authority on the old and new records. | Pending: PostgreSQL no-context, either-context and both-context workflows, enabled/disabled module combinations, cross-tenant and narrow-role refusals, and strict installed row-security status for the new tables. |
| Money | Event and booking charges are owned independently; a linked event cannot raise a venue fee, a replacement never edits the original's price, payment or audit, and staff price confirmation refuses a stale quote before writing. Linked finance never sums across currencies. | Pending: quote/debt/receipt/cancellation/refund/reconciliation journeys with offline and online modes, retained payments, archive, account deletion and concurrency. |
| Notifications and calendars | Direct-room delivery fails closed on a lookup error without spending quota or reaching a provider. Private booking calendar links are pinned to the session owner in the browser (cache privacy only; the API still authorizes every call). | Pending: unknown-state no-send and recovery across all callers, scoped delivery, token privacy and cancellation across calendars. |
| Backup, export, migration and purge | New models and links are classified for export, tenant migration, restore and purge; a retained venue payment that lost its source reference refuses tenant import before a target is created. | A catalogue guard passed on 715 models. Pending: real source/import/restore/purge/RLS/concurrency behaviour for every new model and link. |
| Dependencies and images | Carried from 0.11.0: the production frontend dependency audit recorded zero advisories, with the bounded minimatch development-lint exception described in the [0.11.0 summary](security-summary-0.11.0.md). | **Not clean.** The saved rc4 backend image scan (`sha256:5fee0f410b485c3bb8cebc1e3b447347c9d11adff1c5e97cd8d3505036797c2b`) recorded 240 Debian operating-system package findings (239 high, 1 critical) and no Python package findings; none listed a fixed version. The critical finding is libxml2 CVE-2026-6653, which the Debian security tracker listed as vulnerable for stable (trixie and bookworm) with no stable fix when checked on 8 November 2026. `apt-get upgrade` was already applied. The final 0.12.0 image must be rebuilt and re-scanned by exact digest, with explicit remediation or named, accepted exceptions. Unfixed findings must not be hidden with `--ignore-unfixed` or by mixing unstable packages. The image-slimming candidate and the per-package risk notes, which are pending a rescan, are in [backend image CVE notes](security/backend-image-cve-notes-0.12.0.md). |
| Upgrade and rollback | Forward migrations include database guards and one non-atomic concurrent index build. An image rollback does not undo forward migrations. | Pending: 0.9.2/0.9.3-to-0.12.0 upgrade rehearsal. Rollback is **forward-only by policy**: the updater refuses a downgrade, and restoring the verified pre-update backup is the only supported way back. |

## Findings from the security reviews and how they were closed

An independent read-only review of the 0.12.0 work (five high, eighteen medium and about thirty low findings, none critical), four further read-only reviews of the device, authorization, frontend and architecture slices, a Redis and sign-in audit and a notification and background-job audit were all worked through, high to low. Every finding was verified against the code before it was fixed, and tests were added for the fixes. Detail is deliberately kept at the level of what was protected, not how it could be abused.

| Area | What was wrong | Now |
| --- | --- | --- |
| Profiles and directory | The space member directory ignored the new profile privacy switches and per-project hide; a migration could widen a person's open-web consent; every profile could be enumerated by account number; the spaces and organizations list could show private ones; vouches revealed the voucher's spaces. | The directory honours every switch; opt-outs carry over; lookups are throttled and show non-co-members only name, handle, avatar and public sections; members get a one-time notice that profiles are visible; private spaces, organizations and vouchers stay hidden. |
| Minors | A minor's global profile could be seen platform-wide. | Visible only inside the minor's own spaces; open-web consent needs recorded guardian consent. |
| Usernames and sign-up | Sign-up and the username check could reveal whether an email or login exists; releasing a handle blocked unrelated writes; an unverified sign-up could squat a name; a purged account's name could be re-claimed at once. | Checks answer only available or taken and are throttled; the cooldown blocks only handle changes; reservations hold for a period; the member data export includes the profile. |
| Outbound calls | Anthias, webhook and image-adapter calls could be steered to internal addresses (including through DNS changes and oversized responses), and a Space Manager could reach private networks by default on every edition. | One shared outbound transport pins the connection to the checked address, enforces size and time limits and blocks internal ranges; private LAN players are allowed by default on self-host only; the server's own networks and cloud metadata are always blocked. |
| Display screens | Link secrets were written to access logs; a link could not be rotated; pairing-code claims were unthrottled; a "shown once" secret stayed readable. | Secrets travel in a header and are redacted from logs; rotation works; claims are throttled; the secret is shown once. |
| Device adapter API | Expired commands could be re-delivered; former job owners could read later detections; recordings were never deleted while the audit log said they were; card-verification links could authenticate a borrower; PIN guessing across members; machine scope skipped on adapter routes; adapter-reported minutes billed as sent; logs append-only only in Python; offline decisions could be back-dated. | Command leases expire and are audited; detections are bounded to the job; both storage keys are purged; verification links never authenticate; per-device and per-space attempt budgets with one uniform denial; machine scope everywhere; minutes clamped and flagged; database triggers; bounded decision times. |
| Uploads and storage | A presigned POST could write the final key directly; a failed cut-out store released storage that was never charged; bulk photo upload and template import could hold large amounts of memory or orphan objects; some image paths decoded before checking dimensions. | Every presign lands on the staging key and is promoted once; storage accounting is exact; size, count and dimension checks run before decoding or storing; templates are validated before upload. |
| Machine access | Grants were not scoped to a space and built-in types could not be granted; reports and revoke routes ignored a Machine Manager's scope or leaked existence; the expiry sweep crossed tenants. | Grants and lookups are per space; reports and routes follow machine scope; uniform not-found answers; the sweep is tenant-gated and runs once. |
| Event organisers and templates | Event organisers, including co-host organisation members, could read any saved space card template. | Event organisers can no longer read a space's saved templates. |
| Money and exports | A CSV export could carry spreadsheet formulas; concurrent creators could pass a limit; an oversized platform default raised a server error. | Cells are neutralised; quota checks lock; values are bounded. |
| Frontend | An off-site redirect after URL normalization; unchecked profile link schemes; raw values interpolated into card-studio styles; an inline script blocked by the site's own content security policy. | The redirect target is validated after normalization; schemes are checked; values are escaped; the policy has a baseline and the script moved to a file. |
| Rate limiting and Redis | A Redis outage turned every throttled route, sign-in included, into a server error; a raw email sat in a cache key; some cache keys never expired. | Throttle counters fall back to per-process memory, single-use claims fail closed with a retry, keys are fingerprinted and bounded, a deployment-wide baseline throttle covers every route without its own, and the bundled Redis is pinned with persistence and a memory cap. |
| Sign-in | Removing a last passkey or phone number could lock someone out; a linked identity provider's issuer could be changed; claim codes skipped the login IP guard. | Last-credential removal is refused; slug and issuer lock once linked; claim codes are guarded. See [Sign-in methods](guide/sign-in-methods.md). |
| GitHub on profiles | Anyone could show another person's contribution calendar. | The calendar and badge appear only when the profile owner's linked GitHub sign-in matches the username. |

Items judged hardening rather than a demonstrated weakness were taken too where cheap. The reviews also recorded what was checked and found sound, including tenant scoping on the new routes and signature handling on the adapter API.

The browser/role/module/money matrix, the latest-source backend regression, the final responsive visual review and hosting checks remain pending. No physical CR80 or A4 duplex printer has been tested.

Use [logging and audit](logging-and-audit.md) and the generated [audit action reference](audit-action-reference.md) for action labels, reviewed metadata and request correlation. Keep passwords, credentials, production contact data, private production evidence, signed URLs and tokens out of public logs and screenshots. The final pull request should include the exact commands and results, the exact source and image digests, unresolved exceptions and the accepted real-sample limits from the [release notes](release-0.12.0.md).
