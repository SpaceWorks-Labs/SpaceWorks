# Translating SpaceWorks

SpaceWorks ships in English only, but every screen, API message, email default and PDF label
is ready for translation. This page is for contributors: how to mark new text, what must never
be translated, how to check your work, and how a new language is added later.

The load-bearing rules are in `docs/INVARIANTS.md` → **Internationalisation**. This page is the
how-to.

## The pieces

| Piece | Where |
|---|---|
| The one list of supported languages | `backend/config/supported_locales.json` |
| Backend registry helpers (`LANGUAGES`, validation, canonical codes) | `backend/config/locale_registry.py` |
| Which language a request or an email renders in | `backend/config/locale_resolution.py` |
| The locale middlewares | `backend/config/locale_context.py` |
| Backend catalogue (English) | `backend/locale/en/LC_MESSAGES/django.po` |
| Backend literal guard | `backend/scripts/check_i18n_literals.py` |
| Frontend locale list (generated, committed) | `frontend/src/generated/locales.ts` |
| Frontend runtime: active locale, source, API headers | `frontend/src/lib/i18n.ts`, `frontend/src/lib/localeFetch.ts` |
| Date, number, percent and currency formatting | `frontend/src/lib/format.ts` |
| Frontend catalogue (English) | `frontend/src/locales/en/messages.po` |
| Frontend literal guard | `frontend/scripts/check-i18n-literals.mjs` (positions in `i18n-literal-positions.mjs`) |
| The language switcher | `frontend/src/components/shell/LanguageSwitcher.tsx` |

## Which language wins

Highest first: an explicit choice (the switcher, or `?lang=` on a URL, sent to the API as
`X-SpaceWorks-Locale`), the account's own preference (`User.preferred_locale`, set through
`PATCH /api/v1/auth/me`), the makerspace default (`Makerspace.default_locale`), the browser's
`Accept-Language`, then English. Shared output (a chat message, the makerspace notification
feed, batch PDFs) uses the makerspace default. An email to one account uses that account's
preference, then the makerspace default.

## Marking backend text

- Inside a function, wrap the text in `gettext`:
  `raise ValidationError(gettext("Choose a vendor of this makerspace."))`.
- For Django declarations (model `verbose_name`/`help_text`, serializer `error_messages`), use
  `gettext_lazy`.
- For choice labels and display catalogues (module registry, capabilities, report definitions,
  audit presentation labels, claim refusal reasons), use `gettext_noop`:
  `OPEN = "open", gettext_noop("Open")`. The value stays a plain string, so it is safe in a join,
  a hash or a JSON field. Translate it where it is shown, with
  `config.locale_resolution.display(label)`.
- Put values in with named placeholders, never with an f-string:
  `gettext("Only {remaining} {unit} remain.").format(remaining=left, unit=unit)`.
- Use `ngettext` where the wording depends on a count.
- Email-template **defaults** in `apps/integrations/email_templates_registry*.py` use
  `gettext_noop("...")`. `email_templates.render()` translates them for the recipient. Keep
  the Django template syntax (`{{ ... }}`, `{% ... %}`) exactly as it is.
- Turn a lazy string into `str` inside the active language before it leaves the request. That
  covers SMTP, a chat API, ReportLab, a model field, JSON for Celery, and an `on_commit` callback.
- Render background output inside `config.locale_resolution.override_for(user=..., makerspace=...)`.

## Marking frontend text

- Use the Lingui `t` macro from `@lingui/core/macro` anywhere: JSX text
  (`` <p>{t`Save your changes`}</p> ``), attributes (`` aria-label={t`Close dialog`} ``), objects,
  toasts and errors. Interpolate with a template such as `` t`Delete ${name}` ``.
- A placeholder must be a string or a number. Wrap a value that may be `null` or `undefined`
  in `String(...)` when the old text showed it as is.
- Never mark text in a module that a worker bundles (`scripts/i18n-worker-closure.mjs` lists
  them). The service and preview workers have no Lingui transform. `src/lib/api/errors.ts`
  shows the worker-safe pattern: explicit `i18n._({ id, message })` descriptors.
- Format dates and numbers with `src/lib/format.ts` (`formatDate`, `formatNumber`, ...) or pass
  `formatLocale()`. Never call `toLocale*String()` or `new Intl.*()` without a locale.
- After a change, run `npm run i18n:extract` and commit `src/locales/en/messages.po`.

## Never translate

Stable identifiers stay byte-for-byte. That covers audit `action` and `meta`, API error `code`s,
module, feature, report and notification-event keys, QR target types, object keys, enum values,
URLs, routes, query keys and CSS classes. Translate only their human labels (an audit
presentation label, a choice label, a module title).

Tenant-authored text is never translated. That includes makerspace, product, event and machine
names, descriptions, custom-role names, remarks, custom-form questions and answers, chat-template
bodies, and **edited** email templates.

## Checking your work

Run these from `backend/`:

```bash
python scripts/check_i18n_literals.py          # unmarked text in an output position
python manage.py makemessages -l en --no-obsolete --no-location \
  --ignore=tests/* --ignore=staticfiles/* --ignore=scripts/*   # then diff django.po
```

Run these from `frontend/`:

```bash
npm run i18n:check                  # unmarked copy, including generator output
npm run generate:locales            # after editing supported_locales.json
npm run i18n:extract                # then diff src/locales/en/messages.po
```

Both guards accept a technical string in a checked position when it carries a reason on the
same line or the line above: `# i18n-ignore: <reason>` (Python) or `// i18n-ignore: <reason>`
(TypeScript).

`makemessages` writes a temporary `.py` copy next to every template while it runs. Do not
stage files until it has finished.

## Adding a language later

1. Add `{"code": "<code>", "label": "<the language's own name>"}` to
   `backend/config/supported_locales.json`. Codes are lower case, for example `de` or `pt-br`.
2. Run `npm run generate:locales` and commit `frontend/src/generated/locales.ts`.
3. Run `python manage.py makemessages -l <code> --no-location ...` and translate
   `backend/locale/<code>/LC_MESSAGES/django.po`. The image compiles it.
4. Copy `frontend/src/locales/en/messages.po` to `frontend/src/locales/<code>/messages.po`,
   then translate it.

No migration is needed, because the locale fields validate against the registry and have no
database choices. No code change is needed either: the switcher lists the new language, and
"Use the space's default" appears once more than one language exists. One cost to keep in mind:
every non-English catalogue is bundled eagerly, so each language adds its catalogue to the
initial download.
